# Domain bootstrap method — draft 0.1

This packet is a research and review workbench, not an extension to the production proposal API. The unchanged context-pack 1.3 JSON schema remains authoritative for actual proposal envelopes. Dossier JSON is a local research index; no self-review constitutes approval. Decision is retired from the retained address set by user direction; root, data and calendar are prerequisites/machinery, not disciplinary domains.

1. Draft fifteen observational questions from primary disciplinary sources before drafting vocabulary, and retain their original order and provenance. Later fresh probes and invalid cases must be identified separately; same-agent probes with candidates visible are not independent holdouts. Retain legacy only when its meaning survives source, category and counterexample review. Record retrieved source title, URL, date/edition, section, supported scope and limitations. A reputable publisher does not establish every interpretation attributed to it.
2. Establish imported upper/domain context and mandatory ancestry. The keyword supplies implicit ODO-IM inheritance, but domain derivation must identify an imported usable parent or explicitly record an upstream gap. Only root accesses ODO directly. Never manufacture a parent to make a proposal look complete.
3. Seek five subjects with bearer-specific qualities, five processes with relevant quality parameters, five typed relationships and five bounded events. Five is a coverage target, not a quota: record principled shortfalls. Processes and events record proposed affects/creates/confers bindings and their evidence; an empty binding is preferable to an unsupported causal assertion. Parameters identify qualities, not equations or model inputs embedded in ontology.
4. Audit poorly measured qualities. Attributes, realms and orderings must summarize an identified quality, range or defensible distinction; unspecified 'good', 'resilient' and 'sustainable' are questions, not generic ontology properties. Record boundary/comparison rule, nominal versus ordered values, overlap and contextual scope. Do not invent thresholds or exhaustiveness. Unknown, unmeasured and disputed are evidence states, not automatically predicates. Record viewpoint and missing measurement conventions as unresolved.
5. Write fifteen concrete non-specialist questions per retained domain. For each identify hidden observables, expression, expected category, dependencies, positive and negative cases and source. Distinguish answerability by vocabulary from availability of a model and runtime machinery. A question can require several observable resolutions and a model; do not pretend a sentence is a single executable query.
6. Iterate against questions and record concept/question incidence, unused candidates, missing candidates and ambiguity decisions. Keep full expressions visible; jargon aliases use equals in separate modules, with meaning-tier policy unresolved. Mixed-purpose classifications remain authorities, without automatic equivalence.
7. Validate separately: JSON structure/incidence; actual observable grammar parse; namespace/ancestry/type review; adapter; loaded-worldview semantic validation/reasoner; representative observation/model execution. Each result names exact artifacts and source/tool versions. Parser acceptance cannot discharge a semantic blocker. All expressions are draft until individually checked; no narrative paraphrase is labelled grammar-valid.
8. Human source/domain review, ontology review, exact-revision approval, implementation tests and Git publication are distinct gates. Record actual reviewer identity and decisions only when supplied. Request changes preserves stable asset IDs and evidence; no automated self-approval.

## Change and machinery boundary

All change and cessation require an occurrent. At context time transitions qualities resolve change in X separately; Elevation has no implicit change model. Unresolved change leaves an open-world twin with available knowledge, not inferred zero change or invented retention semantics. Implication and detection are syntax-only here; process-to-role-to-configuration-to-observation consequences are future implementation. Relationships, dependent configurations and substantial cessation must not imply an implemented consequence engine. Models, units, reports, algorithms, equations, variables and generic time/space/scale machinery remain outside domain articulation.

## Instrumentation handoff

Use stable dossier/concept/question/evidence IDs as research references, mapping review-ready concepts into existing proposal assets/evidence/existing_ontologies/alignment/open_questions fields. Do not submit dossier JSON as proposal+yaml. Proposed future stage extensions: source-review ledger, question-semantic test matrix and exact tested artifact hashes; ambiguity-resolution decisions; human approval bindings to proposal revision, action IDs, base commit and artifact hashes. These are requirements for discussion, not new endpoint/attachment contracts. Existing workflow attachment and acceptance limitations remain documented in ../WORKFLOW_TESTS.md and ../REVIEW_WORKFLOW.md.

## Local dossier shape

Each domain folder holds dossier.json and BOOTSTRAP.md. JSON keys: dossier_version, domain, status, scope, imports, sources, concepts, questions, quality_summaries, ambiguities, coverage, validation. Sources use id/title/url/locator/scope/status. Concepts use id/name/category/definition/parent/parent_status/qualities/parameters/bindings/source_ids/positive/negative/status. category is subject/process/relationship/event/quality/predicate. parent is a qualified imported concept or null; parent_status is verified_reference/proposed_parent/blocked. bindings is an object containing source, target, affects, creates, confers as appropriate, with scoped rationale; never imply runtime support. Questions use id/text/concept_ids/expression/expected_type/dependencies/positive/negative/source_ids/semantic_status/grammar_status. expression is a concrete draft observable expression or null with an explanation in dependencies. Semantic statuses remain provisional/blocked; grammar starts untested and changes only through recorded parser results. Quality summaries record quality, proposed_summary, basis, status. Coverage records category shortfalls and weak source areas. Validation explicitly separates source review, grammar, adaptation and semantic/model execution.

The initial schema is intentionally local and versioned independently from the context pack. Backend owners should discuss proposed fields before adopting an interchange contract.

Question intent and expression result are separate: narrative_intent preserves the scientific or methodological request; expression_result_category reports the bounded category audit; expected_type is its compatibility alias, not the narrative's subject. Under context-pack section6, change in a quality yields a process, changed yields an event, and change rate yields a quality. These categories assume a valid operand; the local consistency rule does not validate bearer, type compatibility, references or reasoning. A null full expression may retain components explicitly marked insufficient, with concrete missing observables and dependencies.

Coverage is partial: see COVERAGE_DASHBOARD.md. Six domains meet all four five-record exploration targets; sixteen retain justified shortfalls. Fifteen slots per domain include methodological probes and counterexamples, not fifteen answerable scientific questions. Unknown evidence is not converted into predicate vocabulary to fill a quota.
